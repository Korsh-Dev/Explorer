1. RESUMEN EJECUTIVO
====================================================================================================
El proyecto "Explorer" es una bifurcación moderna de Iquidus Explorer escrita en Node.js, Express,
MongoDB (Mongoose) y Pug. Permite indexar cadenas de bloques basadas en Bitcoin Core y consultar
bloques, transacciones, balances, listas ricas (richlist), mercados y nodos en tiempo real.

Durante la auditoría exhaustiva del código fuente se han detectado:
- 7 Vulnerabilidades Críticas y de Alta Severidad (Bypass de seguridad, XSS Reflejado y Almacenado,
  ReDoS/Inyección de consultas, filtración de credenciales y uso inseguro de eval).
- 8 Errores de Concurrencia Graves causados por el uso no declarado de variables globales (como "i",
  "exMarket" y "split"), que en entornos asíncronos concurrentes provocan corrupción de datos,
  bucles infinitos y colisiones entre peticiones.
- 5 Errores de Lógica y Bloqueo de Ejecución (Precedencia errónea de operadores en JavaScript, bucles
  infinitos en el sincronizador por contadores no incrementados, deadlocks en colas async y
  cálculo erróneo de Content-Length en RPC para caracteres UTF-8 multibyte).
- 4 Puntos de Fallo y Caídas No Controladas (Excepciones no capturadas al recibir respuestas RPC nulas,
  búsquedas malformadas, colas vacías en rate limiting y divisiones por cero con suministro en 0).
- 19 Vulnerabilidades en el árbol de dependencias de npm (5 Críticas, 7 Altas, 7 Moderadas).

[SEC-01] BYPASS DE AUTENTICACIÓN Y CONTROL DE ACCESO RPC MEDIANTE CABECERA 'HOST'
----------------------------------------------------------------------------------------------------
- Ubicación: lib/nodeapi.js (Líneas 105 - 106)
- Severidad: CRÍTICA (CVSS: 9.1)
- Código afectado:
    if ((!settings.api_page.enabled || method_enabled == null || !method_enabled) && req.headers.host.indexOf('127.0.0.1') == -1)
      res.end(settings.localization.method_disabled);
- Descripción del Bug:
  El servidor valida si una solicitud es "interna" comprobando si la cabecera HTTP `Host` contiene
  la cadena `127.0.0.1`. La cabecera `Host` es completamente controlada por el cliente y un atacante
  externo desde Internet puede enviar una petición con:
    GET /api/<metodo_rpc> HTTP/1.1
    Host: 127.0.0.1
  Al contener `127.0.0.1`, la condición evalúa como una petición local interna, permitiendo que
  el atacante invoque métodos RPC no autorizados o métodos que el administrador había deshabilitado.
- Solución propuesta:
  Nunca confiar en `req.headers.host` para autenticación o autorización. Para verificar si una conexión
  proviene de la máquina local se debe inspeccionar la dirección IP remota real (`req.socket.remoteAddress`
  o `req.ip` configurando adecuadamente `trust proxy`):
    const remoteIp = req.socket.remoteAddress;
    const isLocal = remoteIp === '127.0.0.1' || remoteIp === '::1' || remoteIp === '::ffff:127.0.0.1';

[SEC-02] CROSS-SITE SCRIPTING (XSS) REFLEJADO EN PÁGINA DE RECLAMO DE DIRECCIÓN
----------------------------------------------------------------------------------------------------
- Ubicación:
  - routes/index.js (Líneas 403-416, 884)
  - views/claim_address.pug (Líneas 69 - 71)
- Severidad: ALTA (CVSS: 7.5)
- Código afectado:
    if ('!{hash}' != 'null' && '!{hash}' != '') {
      $('#claimAlert').html(generateAlertHTML('info', true, ('!{claim_name}' == '' ? 'Unc' : 'C') + 'laimed address', '<strong>!{hash}</strong> is currently ' + ('!{claim_name}' == '' ? 'un' : '') + 'claimed' + ('!{claim_name}' == '' ? '' : ' as <strong>' + displayAsText('!{claim_name}') + '.</strong>')));
- Descripción del Bug:
  En Pug, la interpolación `!{}` inyecta el valor en bruto sin escapar caracteres HTML o JavaScript.
  La variable `hash` proviene directamente del parámetro de la URL `req.params.hash` en `/claim/:hash`.
  Un atacante puede generar un enlace malicioso como:
    https://explorador.com/claim/';alert(document.cookie);//
  Al abrir la URL, el código malicioso se inserta directamente en el bloque `<script>` de la página,
  ejecutando JavaScript arbitrario en el navegador de la víctima.
- Solución propuesta:
  Utilizar serialización JSON segura (`#{JSON.stringify(hash)}` o pasarlo mediante atributos data en
  elementos HTML) y no inyectar cadenas sin escapar en scripts:
    const safeHash = !{JSON.stringify(hash)};
    const safeClaimName = !{JSON.stringify(claim_name)};

[SEC-03] CROSS-SITE SCRIPTING (XSS) ALMACENADO EN LISTADO DE MASTERNODOS
----------------------------------------------------------------------------------------------------
- Ubicación: views/masternodes.pug (Línea 107)
- Severidad: ALTA (CVSS: 8.2)
- Código afectado:
    json[i]['addr'] = "<a href='/address/" + json[i]['addr'] + "'>" + json[i]['addr'] + ('#{settings.claim_address_page.enabled}' == 'true' && json[i]['claim_name'] != null && json[i]['claim_name'] != '' ? ' <span class="small fw-normal">(' + json[i]['claim_name'] + ')</span>' : '') + "</a>";
- Descripción del Bug:
  Cualquier usuario que sea propietario de una dirección de masternode puede asociarle un nombre

  Sanitizar y escapar entidades HTML en `claim_name` antes de concatenarlo en la tabla o utilizar

[SEC-05] DENEGACIÓN DE SERVICIO (ReDoS) E INYECCIÓN REGEX EN BÚSQUEDA DE DIRECCIONES
----------------------------------------------------------------------------------------------------
- Ubicación: lib/database.js (Línea 34)
- Severidad: ALTA (CVSS: 7.5)
- Código afectado:
    Address.findOne({a_id: {$regex: '^' + hash + '$', $options: 'i'}}).then((address) => { ... })
- Descripción del Bug:
  La variable `hash` proviene directamente de la entrada del usuario en el buscador (`/search` o
  `/ext/getaddress/:hash`). No se escapa ningún carácter especial de expresiones regulares. Si un usuario
  envía patrones con retroceso catastrófico (catastrophic backtracking) como `(a+)+$` o secuencias
  repetitivas, el motor PCRE de MongoDB entra en bucle exponencial, consumiendo el 100% de la CPU
  del servidor de base de datos y dejando el explorador inoperativo para todos los usuarios.
- Solución propuesta:
  Escapar todos los caracteres especiales de regex antes de construir la consulta, o mejor aún,
  validar que `hash` contenga únicamente caracteres alfanuméricos válidos para direcciones criptográficas:
    function escapeRegex(string) {
      return string.replace(/[.*+?^${}()|[\]\\]/g, '\\$&');
    }
    const safePattern = '^' + escapeRegex(hash) + '$';

[SEC-06] USO INSEGURO DE EVAL() PARA CREAR OBJETOS Y CONFIGURACIONES
----------------------------------------------------------------------------------------------------
- Ubicación:
  - app.js (Líneas 579, 597, 602, 1046)
  - lib/settings.js (Líneas 2217, 2221, 2245, 2269, 2291)
- Severidad: ALTA (CVSS: 7.2)
- Código afectado:
    eval('var p_ext = { "last_price_' + currency.toLowerCase() + '": new Decimal(...) ... }');

  Reemplazar `eval()` por la sintaxis estándar de ECMAScript 6 de propiedades computadas y acceso

[CON-01] CONDICIONES DE CARRERA: VARIABLES GLOBALES ACCIDENTALES (global.i, split, exMarket)
----------------------------------------------------------------------------------------------------
- Ubicación:
  - app.js: Línea 446 (`for (i = 0; i < txs.length; i++)`)
  - app.js: Línea 688 (`for (i = 0; i < txs.length; i++)`)
  - app.js: Línea 899 (`for (i = 0; i < masternodes.length; i++)`)
  - app.js: Línea 918 (`for (i = 0; i < rewards.length; i++)`)
  - app.js: Línea 967 (`for (i = 0; i < orphans.length; i++)`)
  - lib/block_sync.js: Línea 383 (`for (i = start; i < (end + 1); i++)`)
  - lib/nodeapi.js: Líneas 137, 305, 310, 320, 329 (`for (i = 0; ... )`)
  - lib/settings.js: Línea 2237 (`for (i = 0; i < split.length - 1; i++)`)
  - lib/explorer.js: Línea 46 (`for (i = 0; i < split.length; i++)`)
  - lib/database.js: Línea 90 (`exMarket = require(...)`)
  - scripts/stop_explorer.js: Línea 20 (`split = stdout.split('\n')`)
- Severidad: ALTA (Impacto severo en estabilidad y concurrencia)
- Descripción del Bug:
  Al no utilizar `'use strict'` ni anteponer `let`, `const` o `var`, Node.js asigna la variable
  directamente al objeto global `global.i`. En un servidor Express asíncrono donde múltiples peticiones
  se atienden en el mismo proceso, si una petición ejecuta un bucle y cede el control en un `await` o
  callback, otra petición modifica `global.i`. Esto genera:
  1) Iteraciones incompletas o saltadas en listas de transacciones y masternodos.
  2) Bucles infinitos si otra petición reinicia el valor de `i`.
  3) Mezcla de datos y respuestas HTTP corruptas.
- Solución propuesta:
  Declarar explícitamente `let i = 0` o `const i` en cada bucle e incluir `'use strict';` al inicio
  de cada módulo para evitar la creación inadvertida de variables globales.

[LOG-01] BUCLE INFINITO EN SINCRONIZACIÓN DE BLOQUES (retryAttempts NUNCA SE INCREMENTA)
----------------------------------------------------------------------------------------------------
- Ubicación: lib/block_sync.js (Líneas 646 - 655)
- Severidad: ALTA
- Código afectado:
    const retryLimit = (10000 / timeout);
    let retryAttempts = 0;

    const handle = setInterval(() => {
      if (tx_counter === 0 || retryAttempts >= retryLimit) {
        clearInterval(handle);
        ...
- Descripción del Bug:
  En el bucle de espera para finalizar el procesamiento de transacciones de un bloque, se define
  un límite de reintentos `retryLimit` y el contador `retryAttempts = 0`. Sin embargo, dentro del
  intervalo NUNCA se ejecuta `retryAttempts++` (a diferencia de la línea 762 donde sí fue implementado).
  Si por algún error o bloqueo `tx_counter` no llega exactamente a 0, la condición `retryAttempts >= retryLimit`
  jamás se cumplirá, creando un bucle infinito que congela por completo el sincronizador de bloques.
- Solución propuesta:
  Agregar `retryAttempts++;` en la rama `else` del callback de `setInterval`:
    if (tx_counter === 0 || retryAttempts >= retryLimit) {
      clearInterval(handle);
      ...
    } else {
      retryAttempts++;
    }

[LOG-02] ERROR DE PRECEDENCIA DE OPERADORES: (!rtx.confirmations > 0)
----------------------------------------------------------------------------------------------------
- Ubicación:
  - routes/index.js (Línea 278)
  - app.js (Línea 507)
- Severidad: MEDIA
- Código afectado:
    if (!rtx.confirmations > 0) {
- Descripción del Bug:
  En JavaScript, el operador de negación lógica `!` tiene mayor precedencia que el operador relacional `>`.
  Por tanto, la expresión evalúa como: `(!rtx.confirmations) > 0`.
  - Si `rtx.confirmations` es 5: `!5` es `false`. `false > 0` evalúa como `0 > 0` que es `false`.
  - Si `rtx.confirmations` es -1 (bloque huérfano): `!-1` es `false`. `false > 0` evalúa como `false`.
  En este último caso (bloques huérfanos con confirmaciones negativas), la lógica falla y no detecta
  que la transacción no está confirmada.
- Solución propuesta:
  Escribir la comparación con paréntesis o verificar directamente:
    if (!(rtx.confirmations > 0)) {
  o bien:
    if (rtx.confirmations == null || rtx.confirmations <= 0) {

[LOG-03] BLOQUEO PERMANENTE (DEADLOCK) EN LA COLA ASYNC.QUEUE DE LIB/BLOCK_SYNC.JS
----------------------------------------------------------------------------------------------------
- Ubicación: lib/block_sync.js (Líneas 397 - 400)
- Severidad: ALTA
- Código afectado:
    const block_queue = async.queue((task, cb) => {
      const { block_height, onComplete } = task;
      const slotIndex = block_numbers.findIndex((v) => v === 0);

      if (slotIndex === -1) {
        setTimeout(() => block_queue.push(task, cb), 1);
        return;
      }
- Descripción del Bug:
  `async.queue` espera que la función trabajadora invoque `cb()` para considerar que la tarea ha
  finalizado y liberar la capacidad concurrente. Cuando `slotIndex === -1` (no hay ranuras libres),
  la función retorna inmediatamente sin llamar a `cb()`. Para `async.queue`, esa ranura queda ocupada
  eternamente, reduciendo la concurrencia disponible hasta provocar un bloqueo total (deadlock) de
  la sincronización.
- Solución propuesta:
  Invocar `cb()` al reprogramar la tarea o manejar la espera mediante un mecanismo de semáforo o promesa:
    if (slotIndex === -1) {
      cb();
      setTimeout(() => block_queue.push(task), 1);
      return;
    }

[LOG-04] CÁLCULO ERRÓNEO DE CONTENT-LENGTH EN CLIENTE JSON-RPC CON CARACTERES MULTIBYTE
----------------------------------------------------------------------------------------------------
- Ubicación: lib/jsonrpc.js (Línea 54)
- Severidad: ALTA
- Código afectado:
    'Content-Length': requestJSON.length
- Descripción del Bug:
  En JavaScript, `string.length` cuenta unidades de código UTF-16, NO la longitud en bytes. Si el cuerpo
  del comando RPC contiene caracteres Unicode multibyte (acentos, símbolos en mensajes OP_RETURN, firmas, etc.),
  `requestJSON.length` será menor que la cantidad real de bytes enviados. El demonio de la blockchain
  recibirá la cabecera `Content-Length` truncada y cortará la petición antes de la llave de cierre `}`,
  generando un error 400 o un fallo de análisis JSON en el nodo.
- Solución propuesta:
  Utilizar la longitud en bytes mediante `Buffer.byteLength`:
    'Content-Length': Buffer.byteLength(requestJSON, 'utf8')

[LOG-05] DOBLE DISPARO DE CALLBACK ERRBACK EN CLIENTE JSON-RPC ANTE ERRORES DE RED
----------------------------------------------------------------------------------------------------
- Ubicación: lib/jsonrpc.js (Líneas 100 y 178)
- Severidad: MEDIA
- Código afectado:
    request.on('error', function(err) {
      if (cbCalled) return;
      cbCalled = true;
      clearTimeout(reqTimeout);
      errback(err);
    });
    ...
    request.on('error', errback);
- Descripción del Bug:
  El evento `'error'` del objeto `request` tiene registrados DOS listeners: el listener personalizado
  en la línea 100 y la llamada directa `request.on('error', errback)` en la línea 178. Cuando ocurre
  un error a nivel de socket o conexión rechazada, `errback` es llamado dos veces, lo que produce
  errores de cabeceras ya enviadas (`ERR_HTTP_HEADERS_SENT`) o excepciones no capturadas.
- Solución propuesta:
  Eliminar la línea 178 (`request.on('error', errback);`) ya que el listener de la línea 100 ya gestiona
  correctamente el timeout, la bandera `cbCalled` y la invocación a `errback`.

[LOG-06] CAÍDA DEL PROCESO POR DESREFERENCIA NULA EN RESPUESTA RPC MALFORMADA
----------------------------------------------------------------------------------------------------
- Ubicación: lib/jsonrpc.js (Líneas 164 - 173)
- Severidad: ALTA
- Código afectado:
    } else {
      if (errback) {
        err = new Error(decodedResponse.error.message || '');
        if (decodedResponse.error.code)
          err.code = decodedResponse.error.code;
        errback(err);
      }
    }
- Descripción del Bug:
  Si la respuesta RPC no contiene `result` y tampoco contiene `error` (o `error` es `null`), el flujo
  entra en la rama `else`. En esta rama se intenta acceder a `decodedResponse.error.message`. Al ser
  `decodedResponse.error` nulo o indefinido, Node.js lanza `TypeError: Cannot read properties of undefined (reading 'message')`.
  Al ocurrir dentro del evento `response.on('end')` fuera de un bloque `try/catch`, esto resulta en una
  excepción no capturada que tumba inmediatamente el proceso del servidor.
- Solución propuesta:
  Verificar la existencia de `decodedResponse.error` antes de desreferenciar sus propiedades:
    const errMsg = (decodedResponse.error && decodedResponse.error.message) ? decodedResponse.error.message : 'Respuesta RPC inválida o vacía';
    err = new Error(errMsg);
    if (decodedResponse.error && decodedResponse.error.code)
      err.code = decodedResponse.error.code;

- Descripción del Bug:
  A diferencia de otras funciones en `explorer.js` (como las líneas 869 y 896), en la llamada a
  `verifymessage` no se codifican los parámetros. Si el mensaje que el usuario firma contiene espacios,
  símbolos como `&`, `+`, `#` o `=`, la URL se rompe y los parámetros llegan incompletos al nodo,
  haciendo que la verificación de firma criptográfica falle siempre para mensajes con caracteres especiales.
- Solución propuesta:
  Codificar adecuadamente todos los componentes del querystring:
    const uri = `${base_url}verifymessage?address=${encodeURIComponent(address)}&signature=${encodeURIComponent(signature)}&message=${encodeURIComponent(message)}`;

[LOG-09] EXCEPCIÓN TYPEERROR (fn is not a function) EN GESTOR DE RATE LIMITING
----------------------------------------------------------------------------------------------------
- Ubicación: lib/ratelimit.js (Líneas 29 y 42)
- Severidad: MEDIA
- Código afectado:
    if (this._queue.length === 0) {
      this._numOps++;
      fn();
    ...
    setTimeout(function() {
      that.schedule();
    }, 1 / this._maxRate);
- Descripción del Bug:
  Cuando se reprograma la ejecución mediante `setTimeout`, se invoca `that.schedule()` sin argumentos
  (`fn` es `undefined`). Si en el momento de ejecutarse `this._queue` se encuentra vacía, el código entra
  en `this._numOps++; fn();`, ejecutando `undefined()`, lo que arroja un `TypeError: fn is not a function`.
- Solución propuesta:
  Comprobar siempre que `fn` sea una función antes de invocarla directamente:
    if (this._queue.length === 0) {
      if (typeof fn === 'function') {
        this._numOps++;
        fn();
      }
    }

[LOG-11] POSIBLE DIVISIÓN POR CERO EN DISTRIBUCIÓN DE RIQUEZA (stats.supply == 0)

[DEP-01] FALLO DE PARSEO EN SCRIPT DE DETENCIÓN (stop_explorer.js) EN WINDOWS
----------------------------------------------------------------------------------------------------
- Ubicación: scripts/stop_explorer.js (Línea 20)
- Severidad: MEDIA
- Código afectado:
    split = stdout.split('\n');
    return cb(`taskkill /f /pid ${split[0]}`);
- Descripción del Bug:
  En Windows, la salida del comando CMD termina con `\r\n`. Al hacer `stdout.split('\n')`, el elemento
  `split[0]` conserva el retorno de carro `\r`. Al ejecutar `taskkill /f /pid 1234\r`, el comando falla
  con error de sintaxis en el PID. Adicionalmente, la variable `split` no está declarada con `let`/`const`.
- Solución propuesta:
  Limpiar espacios y caracteres de salto de línea:
    const pid = split[0].trim();
    return cb(`taskkill /f /pid ${pid}`);

[DEP-02] DETECCIÓN DE RAMA GIT ROTA EN ACTUALIZADOR (update_explorer.js)
----------------------------------------------------------------------------------------------------
- Ubicación: scripts/update_explorer.js (Línea 31)
- Severidad: BAJA
- Código afectado:
    if (fs.existsSync('./.git') && fs.existsSync('./.git/refs/heads/master'))
- Descripción del Bug:
  El script asume que la rama local siempre es `master` y que el archivo `.git/refs/heads/master`
  existe en disco. Si el repositorio utiliza la rama por defecto moderna `main`, o si git ha empaquetado

  de git, impidiendo actualizaciones automáticas.
- Solución propuesta:
